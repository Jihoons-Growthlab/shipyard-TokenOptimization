# SWP Shipyard: 명세 기반 재구현과 Claude Code 토큰 사용량 비교

조선소 통합관리 시스템을 [`specs/`](specs/index.md)의 명세와 [`reference/`](reference/ui/README.md)의 참고 자료만으로 새로 구현한 프로젝트입니다. 이 저장소는 애플리케이션 자체와 함께, Claude Code 재구현 과정에서 토큰 사용 구조를 어떻게 바꾸었는지와 그 측정 결과를 기록합니다.

| 지표 | 최적화 전 | 최적화 후 | 변화 |
|---|---:|---:|---:|
| 총 토큰 | 64,895,120 | 20,995,581 | **-67.6%** |
| API 응답 수 | 425 | 63 | -85.2% |
| 응답당 평균 입력 컨텍스트 | 152,990 | 328,801 | +114.9% |

> 두 수치는 조건이 같은 대조 실험의 결과가 아닙니다. 최적화 후 실행은 최적화 전 완성본에서 뽑아낸 명세와 이미지를 입력으로 사용했습니다. 토큰 감소율은 비용 감소율이 아니며, 두 결과물의 품질이 같다는 것도 검증되지 않았습니다. 자세한 내용은 [해석과 한계](#해석과-한계)에 있습니다.

## 프로젝트 개요

## 실행 방법

### 사전 준비

- Python 3.10 이상, [uv](https://docs.astral.sh/uv/)
- Node.js 18, 20 또는 22 이상 (19, 21 제외), npm
- Unity 6000.5.10f1과 Web Build Support (3D 뷰어를 빌드할 때만 필요)

### 백엔드

```bash
cd backend
uv run init-db --seed
uv run uvicorn app.main:app --port 8000
```

`init-db --seed`는 마이그레이션을 적용하고 시드를 적재합니다. 환경 변수는 [`backend/.env.example`](backend/.env.example)을 참고하세요. `APP_SECRET`을 지정하지 않으면 프로세스마다 난수를 쓰므로 서버를 재시작할 때 로그인이 풀립니다.

### 프론트엔드

새 터미널에서 실행합니다.

```bash
cd frontend
npm install
npm run dev
```

`http://127.0.0.1:5173`으로 접속합니다. Vite가 `/api`를 `127.0.0.1:8000`으로 프록시합니다. 프로덕션 정적 제공은 구현되어 있지 않아 Vite(dev 또는 preview)로 실행합니다.

데모 계정은 [`reference/seed/seed.json`](reference/seed/seed.json)의 `users`에 있습니다. `admin`, `lee.dwg`는 OTP를 사용하며 코드는 `totp_secret`으로 계산합니다. 이 값들은 데모 전용입니다.

### 3D 뷰어

빌드 결과(`frontend/public/unity/`)는 Git에서 제외되므로, 저장소를 새로 받으면 3D 탭을 쓰기 전에 빌드해야 합니다.

```bash
sh unity/build.sh
```

기본 Unity 경로는 스크립트에 있으며 `UNITY` 환경 변수로 바꿀 수 있습니다. 같은 프로젝트를 Editor로 열어 둔 상태에서는 실패합니다.

### 테스트

```bash
cd backend && uv run pytest -q
cd frontend && npm test
cd frontend && npm run build
```

### 재구현 재현

Claude Code에서 `/rebuild`를 입력하면 [`PROGRESS.md`](PROGRESS.md)의 다음 단계부터 진행합니다. 이 저장소는 이미 12단계가 완료된 상태이므로, 재현하려면 구현 폴더와 진행 기록을 뺀 별도 복사본에서 실행해야 합니다.

## 최적화 전후 비교

- **최적화 전:** 별도 로컬 저장소 `shipyard-claude`의 작업입니다. 공개 문서는 [`READMEBefore.md`](READMEBefore.md)에 보존했습니다.
- **최적화 후:** 이 저장소입니다. `shipyard-claude`에서 만든 `rebuild-starter/` 패키지로 시작했으며, 현재 지침과 명세가 그 패키지와 같은 내용인지 비교해 README를 제외하고 일치함을 확인했습니다.

`shipyard-claude` 저장소와 세션 로그는 이 저장소에 포함되어 있지 않습니다. 아래 before 수치 중 `READMEBefore.md`에 없는 값은 로컬 자료를 직접 확인한 결과이며, 외부 독자가 재현할 수는 없습니다.

| 항목 | 최적화 전 | 최적화 후 |
|---|---|---|
| 작업 방식 | 사람이 단계마다 지시 (프롬프트 28개) | `/rebuild` 1회로 12단계 진행 |
| 세션 | 8개 | 1개 |
| 구현 기준 자료 | HTML 목업(123,762바이트), 기능·아키텍처 문서 16개(59,045바이트), 사용자 캡처 12장 | 명세 15개(74,071바이트), 완성본 캡처 29장, 시드(45,855바이트) |
| 공통 지침 | `CLAUDE.md` 1,135바이트, `.claude/rules/` 5개 2,497바이트 (4개는 경로 지정) | `CLAUDE.md` 2,055바이트, rules 없음 |
| 스킬 | `implement-feature` (기능 하나씩 호출) | `rebuild` (전체 단계 반복) |
| 진행 기록 | `docs/handoffs/` 문서 8개(56,793바이트), `status.md` 212줄 | `PROGRESS.md` 1개(1,054바이트), 40줄 제한으로 덮어쓰기 |
| MCP 설정 | Playwright(`@latest`), Context7, SQLite | Playwright(`@0.0.84`)만 |
| 프로젝트 권한 허용 목록 | `.claude/settings.json` 비어 있음 | 자주 쓰는 명령과 Playwright를 허용 |
| Git 제외 목록 | 9개 항목 | Unity 캐시, 빌드 결과, 로그 등 추가 |

크기가 커진 항목도 있습니다. `CLAUDE.md`와 스킬 파일은 오히려 늘었고 명세도 약 25% 늘었습니다. 지침 파일을 짧게 만든 것이 이번 변화의 핵심은 아닙니다.

**확인할 수 없어 비교에서 제외한 항목**

- `READMEBefore.md`의 멀티 터미널 운영은 터미널 구성이 기록에 남지 않아 비교하지 않았습니다.
- 영어 중심 프롬프트는 최적화 후 사람이 입력한 프롬프트가 `/rebuild` 하나뿐이라 비교할 대상이 없습니다.

## 적용 기법

아래의 "원리"는 토큰에 영향을 줄 수 있는 경로를 설명합니다. 기법별 절감 기여도는 측정하지 않았으며, 각 기법을 따로 켜고 끈 실험도 없습니다.

| 기법 | 적용 상태 |
|---|---|
| 1. 명세 기반 재구현 | 적용 |
| 2. 지침과 명세 분리 | 적용 (최적화 전에도 일부 존재) |
| 3. 단계별 정보 로딩 | 적용, 로그로 확인 |
| 4. 검색 범위와 출력 제한 | 지침으로 적용, 강제 장치 없음 |
| 5. 진행 상태 외부 기록 | 적용, 복구에 쓰이지는 않음 |
| 6. 대화 압축 지침 | 설정됨, 측정 실행에서 압축이 발생하지 않음 |
| 7. 스킬을 통한 작업 절차 표준화 | 적용 |

### 1. 명세 기반 재구현

- **이전:** HTML 목업과 초기 기능 명세를 바탕으로 구현했고, 미결정 사항을 결정 문서로 관리하며 진행했습니다.
- **변경:** 완성본의 동작을 명세로 정리해 구현 순서, 공통 판단 기준, 알려진 동작, 미확정 사항까지 [`specs/index.md`](specs/index.md)에 확정했습니다.
- **원리:** 결정이 이미 문서에 있으면 탐색과 질의, 재작업에 쓰이는 왕복이 줄어들 수 있습니다. 응답마다 누적 컨텍스트가 다시 처리되므로 왕복 수는 캐시 읽기 토큰과 직접 연결됩니다.
- **관련 파일:** [`specs/index.md`](specs/index.md), [`specs/foundation.md`](specs/foundation.md), [`specs/data-model.md`](specs/data-model.md), [`specs/rules.md`](specs/rules.md), [`reference/ui/README.md`](reference/ui/README.md)

### 2. 지침과 명세 분리

- **이전:** `CLAUDE.md`, 경로별 rules, 기능 명세, 아키텍처 문서, 인수인계 문서로 나뉘어 있었습니다.
- **변경:** 항상 적용할 원칙은 `CLAUDE.md`, 절차는 스킬, 요구사항은 명세, 진행 상태는 `PROGRESS.md`로 정리했습니다. 인덱스에는 순서와 공통 기준만 두고 요구사항 원문은 각 명세에만 둡니다.
- **원리:** 세션 내내 컨텍스트에 남는 지침과 필요할 때만 읽는 자료를 나누면, 특정 단계에서만 필요한 내용이 모든 응답에 실리는 것을 피할 수 있습니다.
- **관련 파일:** [`CLAUDE.md`](CLAUDE.md), [`.claude/skills/rebuild/SKILL.md`](.claude/skills/rebuild/SKILL.md), [`specs/index.md`](specs/index.md)

### 3. 단계별 정보 로딩

- **이전:** 기능 단위 읽기 규칙은 있었지만, 무엇을 언제 읽을지는 사람의 프롬프트와 작업 흐름에 달려 있었습니다.
- **변경:** 12단계마다 읽을 명세와 이미지를 표로 지정했습니다. `CLAUDE.md`는 현재 단계의 자료만 열도록 규정합니다.
- **원리:** 아직 필요 없는 자료가 초반에 컨텍스트에 들어가면 이후 모든 응답이 그 내용을 다시 읽습니다. 로딩 시점을 늦추면 그만큼 누적을 늦출 수 있습니다.
- **실행 확인:** 세션 로그에서 이미지와 명세가 대체로 단계 순서대로 열린 것을 확인했습니다. 다만 단계 7과 8의 자료는 한 번에 열렸고, 단계 3에서 뒤 단계 명세를 `grep`으로 조회한 기록도 있습니다.
- **관련 파일:** [`specs/index.md`](specs/index.md), [`CLAUDE.md`](CLAUDE.md)

### 4. 검색 범위와 출력 제한

- **이전:** 파일 읽기 규칙([`READMEBefore.md`](READMEBefore.md)의 Selective File Reading)은 있었습니다. 다만 도구 출력이 많았고 텍스트 결과만 약 150만 자였습니다.
- **변경:** 검색 폴더 제한, 파일 전체 출력 금지, 긴 로그는 오류 구간만 보기, 시드는 코드로 적재, `.gitignore` 대상 제외를 지침으로 명시했습니다. 다시 볼 출력은 `logs/`에 저장하고 경로만 기록합니다.
- **원리:** 도구 출력은 대화에 남아 이후 응답의 컨텍스트가 됩니다. 한 번 크게 출력되면 그 뒤의 모든 응답에 비용이 반복됩니다.
- **한계:** Hook 같은 강제 장치 없이 지침으로만 적용했습니다. 실행에서는 `grep`, `cut`, `tail` 사용이 확인되지만, 현재 단계의 명세는 `cat`으로 전체를 읽기도 했습니다.
- **관련 파일:** [`CLAUDE.md`](CLAUDE.md), [`.gitignore`](.gitignore)

### 5. 진행 상태 외부 기록

- **이전:** 인수인계 문서 8개에 진행 상태, 결정, 도구 증빙을 나누어 기록했고 `status.md`는 212줄까지 누적되었습니다.
- **변경:** `PROGRESS.md` 하나만 쓰고, 40줄 이내로 덮어씁니다. 현재 단계, 완료 기준, 핵심 결정, 변경 파일, 실패한 검증, 다음 작업만 남깁니다.
- **원리:** 세션이 끊겨도 대화 전체를 복원하지 않고 짧은 파일에서 재개할 수 있고, 누적하지 않으므로 읽는 비용이 일정 범위에 머뭅니다.
- **실행 확인:** 측정 실행은 세션 하나로 끝나 재개 기능은 쓰이지 않았습니다. 진행 기록 갱신만 있었습니다.
- **관련 파일:** [`PROGRESS.md`](PROGRESS.md), [`.claude/skills/rebuild/SKILL.md`](.claude/skills/rebuild/SKILL.md)

### 6. 대화 압축 지침

- **이전:** 압축 시 남길 내용에 대한 프로젝트 지침이 없었고, 세션 전환과 인수인계 문서로 맥락을 이어 갔습니다.
- **변경:** `CLAUDE.md`의 Compact Instructions에 목표, 사용자 제약, 현재 단계, 미해결 오류, 검증 상태를 남기도록 지정했습니다. 스킬은 `/clear`를 금지하고 압축은 자동 압축에 맡기며, 불확실하면 추측하지 말고 진행 기록과 명세를 다시 읽게 합니다.
- **원리:** 압축이 일어나면 그 뒤 컨텍스트는 요약본이 됩니다. 요약에 필요한 정보가 남아야 같은 내용을 다시 읽거나 재작업하는 일을 줄일 수 있습니다.
- **실행 확인:** 측정 세션 로그에 압축 기록이 없습니다. 따라서 이 지침은 이번 측정값에 영향을 주지 않았다고 봐야 합니다.
- **관련 파일:** [`CLAUDE.md`](CLAUDE.md), [`.claude/skills/rebuild/SKILL.md`](.claude/skills/rebuild/SKILL.md)

### 7. 스킬을 통한 작업 절차 표준화

- **이전:** `/implement-feature F04`처럼 기능마다 호출했고, 범위와 제약을 프롬프트로 추가했습니다. 일부 작업은 스킬 없이 진행했습니다.
- **변경:** `/rebuild`가 확인, 읽기, 구현, 검증, 기록, 계속의 순서를 마지막 단계까지 반복합니다. 멈추는 조건도 사용자만 할 수 있는 조치가 필요할 때로 제한했습니다.
- **원리:** 같은 절차를 프롬프트로 반복 전달할 필요가 없고, 사람의 확인을 기다리며 새로 쌓이는 왕복이 줄어들 수 있습니다. 스킬 파일 자체는 약 2.3KB로, 호출하면 그만큼 컨텍스트에 들어갑니다.
- **관련 파일:** [`.claude/skills/rebuild/SKILL.md`](.claude/skills/rebuild/SKILL.md)

### 그 밖의 변경: MCP 구성 축소

- **이전:** Playwright, Context7, SQLite를 설정했습니다. 로그에서 Context7과 SQLite는 MCP 평가 중의 연결 시험 외에 실제 호출이 확인되지 않았습니다.
- **변경:** [`.mcp.json`](.mcp.json)에는 버전을 고정한 Playwright만 남겼고, [`.claude/settings.json`](.claude/settings.json)에서 이 서버만 활성화합니다.
- **원리:** 쓰지 않는 도구가 사라져 도구 선택지와 관련 정의가 줄어듭니다. 다만 절감량은 측정하지 않았습니다.

## `/rebuild`와 Playwright MCP의 역할

| 구분 | `/rebuild` | Playwright MCP |
|---|---|---|
| 정체 | 사용자가 호출하는 커스텀 스킬 | 브라우저를 조작하는 외부 도구 서버 |
| 하는 일 | 작업 절차를 지시 | 화면 열기, 입력, 스크린샷 등 검증 동작을 수행 |
| 정의 위치 | [`.claude/skills/rebuild/SKILL.md`](.claude/skills/rebuild/SKILL.md) | [`.mcp.json`](.mcp.json) |
| 호출 방식 | 사용자가 입력 (`disable-model-invocation: true`로 모델이 자동 호출하지 않음) | 스킬의 검증 단계에서 Claude가 도구로 호출 |

둘 중 어느 쪽도 그 자체로 토큰을 줄이지 않습니다. 스킬 본문과 도구 입출력은 오히려 컨텍스트에 추가됩니다. 토큰 사용량을 좌우하는 것은 이들을 어떤 범위와 빈도로 쓰느냐입니다. 측정 실행에서는 Playwright 호출 32건 중 27건이 스크립트 실행 방식(`browser_run_code_unsafe`)이었고, 여러 조작을 한 호출에 묶었습니다.

### 전체 입력을 함께 봐야 하는 이유

일반 입력 토큰만 보면 920에서 130으로 줄어든 것처럼 보이지만, 이 항목은 전체의 극히 일부입니다. 모델에 들어간 입력은 일반 입력, 캐시 생성, 캐시 읽기를 합쳐서 봐야 합니다.

| 전체 입력 | 최적화 전 | 최적화 후 | 감소율 |
|---|---:|---:|---:|
| 일반 입력 + 캐시 생성 + 캐시 읽기 | 64,317,051 | 20,714,524 | 67.8% |

캐시 읽기는 합계의 97.0%(전), 96.4%(후)를 차지합니다. 그래서 합계의 변화는 사실상 캐시 읽기의 변화입니다. 다만 토큰 종류마다 요금 단가가 다르므로 이 단순 합계는 비용을 나타내지 않습니다.

### 집계 방식

| 구분 | 최적화 전 | 최적화 후 |
|---|---|---|
| 대상 | `shipyard-claude` 세션 로그 전체 (서브에이전트 포함) | 세션 `7ddba5fd` 1개 |
| 기간 (KST) | 2026-11-03 22:14 ~ 2026-11-04 21:26:32 | 2026-11-04 22:21 ~ 23:07 |
| 수치 출처 | MCP 평가 작업 중의 임시 집계 | [`extract_usage.py`](extract_usage.py) 결과 [`usage-final.json`](usage-final.json) |
| 재검증 | 로그를 시점순으로 누적해 해당 시각에서 4개 항목이 모두 일치 | 스크립트 재실행 결과가 파일과 일치 |

[`extract_usage.py`](extract_usage.py)의 동작을 코드와 실제 로그로 확인한 결과입니다.

- **응답 ID 중복 제거:** `message.id`를 키로 사용하며 같은 ID는 마지막 값을 씁니다. 측정 세션에서는 사용량이 포함된 209줄이 63개 응답으로 정리됩니다.
- **제외 대상:** 모델이 `<synthetic>`인 항목은 제외합니다. 최적화 전 구간의 2건이며 제외해도 토큰 합계는 같습니다.
- **집계 범위:** 현재 폴더 경로의 영문·숫자 외 문자를 `-`로 바꾼 폴더를 찾아 그 안의 모든 세션을 합칩니다. 다른 프로젝트는 섞이지 않지만, 같은 폴더의 다른 세션은 포함됩니다.
- **서브에이전트:** 코드 주석은 포함한다고 적혀 있지만, `*.jsonl`을 재귀 없이 찾기 때문에 `<세션>/subagents/` 파일은 **포함되지 않습니다.** `shipyard-claude` 전체 기준으로 비재귀 85,473,891, 재귀 86,623,412로 1,149,521 차이가 납니다. 제공된 최적화 전 수치는 서브에이전트를 포함한 값이고, 최적화 후에는 서브에이전트가 없어 이 차이가 결과에 영향을 주지 않습니다.
- **스킬과 프롬프트 집계:** `usage-final.json`의 `skills`가 비어 있고 `prompts`가 0개인 것은 `/rebuild`를 쓰지 않았다는 뜻이 아닙니다. 스크립트가 명령 태그를 제거하고 모델의 `Skill` 도구 호출만 세기 때문이며, 로그에는 `/rebuild` 입력이 남아 있습니다.

### 결론을 제한하는 요인

1. **완성본의 지식이 입력에 포함되었습니다.** 명세의 알려진 동작, [화면 이미지](reference/ui/README.md), 시드, 로그인 배경 SVG는 최적화 전 완성본에서 나왔습니다. 최적화 후 실행은 설계 결정과 시행착오를 이미 끝낸 상태에서 시작했습니다.
2. **준비 비용이 어느 쪽 수치에도 없습니다.** 최적화 전 수치는 2026-11-04 21:26:32 시점에서 끊긴 값입니다. 이후 MCP 평가와 시작 패키지 제작에 45개 응답, 21,728,292토큰이 쓰였습니다. 참고로 이를 최적화 후에 더하면 42,723,873토큰이고 감소율은 34.2%가 됩니다. 이 구간에 패키지 제작 외의 작업도 섞여 있어 정확한 준비 비용은 아니며, 67.6%를 대체하는 값도 아닙니다.
3. **최적화 전 수치에 범위 밖 작업이 일부 있습니다.** 스냅샷 직전의 MCP 평가 시작 구간이 포함되고, 초기 계획과 MCP 설정, 사용자의 UI 변경 요청도 포함됩니다.
4. **외부에서 만든 자료는 측정되지 않았습니다.** 초기 명세는 Git 기록상 다른 도구와의 대화로 작성되었으며, 이 토큰은 어느 수치에도 없습니다.
5. **반복 실험이 아닙니다.** 양쪽 모두 1회 실행이고 순서도 고정되어 있어 편차를 알 수 없습니다.
6. **단계별 토큰이 없습니다.** 최적화 후 실행은 프롬프트가 하나라 단계별로 분해되어 있지 않습니다.

### 알 수 있는 것과 없는 것

| 말할 수 있는 것 | 말할 수 없는 것 |
|---|---|
| 기록된 두 작업의 토큰 합계는 67.6% 차이가 난다 | 비용이 67.6% 줄었다 |
| 차이는 대부분 캐시 읽기에서 나왔고, 응답 수 감소가 직접 요인이다 | 어떤 기법이 몇 퍼센트를 절감했는가 |
| 확정된 명세와 절차로 12단계를 한 번의 지시로 완료했다 | 같은 품질이 유지되었다 |
| 측정 실행의 테스트와 브라우저 시나리오는 기록상 통과했다 | 새 프로젝트에서도 같은 감소율이 나온다 |

최적화 후 실행의 알려진 잔여 사항도 있습니다. 화면 비교 후 카드 제목 여백을 조정했으나 전체 재측정은 하지 않았고, 셀렉트 화살표와 글자 위치가 1px 달라진 현상의 원인은 찾지 못했습니다. Unity 압축 빌드와 실제 배포 서버 헤더는 검증하지 않았습니다.

공정한 비교를 위해서는 최적화 전 구현 구간만 분리하고, 준비 비용을 별도 항목으로 계상하며, 같은 명세에서 조건을 바꾼 반복 실행과 공통 수용 시나리오가 필요합니다. [`CLAUDE.md`](CLAUDE.md)는 토큰을 아끼려고 기능, 필요한 추론, 테스트, 화면 확인을 줄이지 않도록 규정하고 있으며, 이 원칙이 지켜졌는지도 그런 공통 시나리오로 확인해야 합니다.
